# OIDC-Implementation

A module-based OpenID Connect Authorization Server built on Express + TypeScript +
Drizzle + PostgreSQL, using [`oidc-provider`](https://github.com/panva/node-oidc-provider)
for spec-compliant token issuance and a pluggable identity-provider layer for
social login (Google, GitHub — extensible to more).

---

## Requirements

- Node.js (LTS)
- Docker (for local Postgres)
- `openssl` (for key generation — included with Git Bash on Windows, or use WSL)

---

## First-time setup

Run these in order. **Do not skip the key generation step** — the server will
refuse to start without it.

```bash
# 1. Start Postgres
docker compose up -d

# 2. Generate OIDC signing keys (RSA-2048 -> keys/private.pem, public.pem, jwks.json)
bash key-gen.sh
# or
npm run keys:generate

# 3. Install dependencies
npm install

# 4. Copy and fill in environment variables
cp .env.example .env

# 5. Run database migrations
npm run db:generate
npm run db:migrate

# 6. Start the dev server
npm run dev
```

The server listens on `PORT` from `.env` (default `8080`).

```
└── modules/
    ├── keys/                     # Loads signing keys generated by key-gen.sh
    ├── users/                    # User + identity linking repository
    ├── identity-providers/       # Pluggable social login (google/, github/, core/)
    ├── auth/                     # Login page, session, logout
    └── oidc/                     # oidc-provider config, Drizzle adapter, interaction handler
```

## Auth flow (high level)

1. Relying party redirects the user to `/auth` (the OIDC authorization endpoint).
2. If there's no session, `oidc-provider` sends the user to the login interaction.
3. User picks "Continue with Google" or "Continue with GitHub".
4. The identity-providers module completes the upstream OAuth exchange and
links or creates a user in the database.
5. If the client is requesting scopes not yet granted, the user sees a consent
interaction before continuing.
6. A session cookie is set and the OIDC interaction is marked complete.
7. `oidc-provider` issues an authorization code; the client exchanges it at
`/token` for an `id_token` and `access_token`.

## Logout behavior

`POST /logout` does two things: destroys the local Express session **and**
revokes the user's active `oidc-provider` grants via the adapter. This prevents
a "logged out" user from silently obtaining a new access token from a
lingering refresh token.

## Adding a new identity provider

1. Create `src/modules/identity-providers/<name>/`.
2. Implement the `IdentityProvider` interface (`isEnabled`,
`getAuthorizationUrl`, `exchangeCodeForProfile`).
3. Add the provider's env vars to `src/common/config/env.ts`.
4. Register it in `src/modules/identity-providers/index.ts`:
   `registry.register(new YourProvider(env))`.
5. Add a login button on the login page by looping over
   `registry.listEnabled()`.

### Future provider checklist

1. Create the provider folder under `src/modules/identity-providers/<name>/`.
2. Implement `IdentityProvider` for the provider-specific OAuth flow.
3. Add and document the required env vars in `src/common/config/env.ts`.
4. Register the provider in `src/modules/identity-providers/index.ts`.
5. Expose it on the login page via the enabled-provider loop.

## Security notes

- PKCE is required for all clients.
- Upstream OAuth redirects use a `state` parameter, stored in `oauth_states`
with a 10-minute expiry.
- Session cookies are `httpOnly`, `secure` in production, `sameSite: lax`.
- Client secrets are hashed (bcrypt/argon2) if stored in the database.
- `/token` and `/auth/external/*` are rate-limited.
- Auth failures are logged without leaking secrets or tokens.

## What not to change

- `docker-compose.yml` — already correct for local Postgres.
- `dist/` — build output, regenerated by `npm run build`.
- Don't create `src/db/` — schema lives in `src/common/db/`.
